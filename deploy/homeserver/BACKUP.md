# Резервные копии базы Report

Вся база — один файл SQLite `~/report/data/data.db`. В нём проекты, отчёты,
история прогонов, хэши паролей и **OAuth-токены Яндекса и Google открытым
текстом**. Потеря файла означает заново подключать все интеграции; утечка файла
означает доступ к чужим рекламным кабинетам, поэтому копии лежат с правами
`0600` в каталоге `0700`, и восстановление эти права не ослабляет.

## Как это устроено

| | |
|---|---|
| Что копируется | `~/report/data/data.db` |
| Куда | `~/backups/report/data-YYYYmmdd-HHMMSSZ.db` (время UTC) |
| Когда | ежедневно в 03:30, `report-backup.timer` |
| Проверка | ежедневно в 12:00, `report-backup-check.timer` |
| Хранение | 30 дней, но не меньше 7 последних копий |
| Инструмент | `backend/scripts/backup_db.py` (только стандартная библиотека) |

Останавливать сервис не нужно: копия снимается онлайн, на работающей базе.

Копией считается **только** файл вида `data-YYYYmmdd-HHMMSSZ.db`. Положить рядом
свой снимок можно, но назовите его иначе (например `manual-before-upgrade.db`) —
скрипт его не тронет и не спутает с настоящей копией. Файл с посторонним именем
скрипт назовёт в предупреждениях, чтобы про него не забыли.

### Почему не `cp data.db`

Так делал старый крон на ВМ — и это было опасно. База работает в режиме **WAL**:
зафиксированные транзакции какое-то время лежат в отдельном файле `data.db-wal`
и попадают в основной файл только при чекпоинте. `cp` одного `data.db`:

* молча теряет всё, что ещё не зачекпоинчено, — копия выглядит целой, но отстаёт;
* снятая посреди чекпоинта, может оказаться порванной.

`backup_db.py` использует онлайн-бэкап SQLite (`sqlite3.Connection.backup`) —
согласованный снимок под коротким read-lock. Регресс закреплён тестом
`backend/tests/test_backup.py::TestWalSafety` (он же показывает, что наивная
копия действительно теряет строку).

### Что значит «проверено»

Проверки делятся на **жёсткие** и **мягкие**, и различие принципиально.

**Жёсткие** — копия негодна, файл удаляется, копии за этот запуск нет:
файл не открывается, `PRAGMA integrity_check` не `ok`, нет таблиц приложения,
ноль пользователей. Файл с финальным именем в каталоге — всегда прошедший их.

**Мягкие** — копия снята и годна, но на неё стоит посмотреть: нарушенные внешние
ключи в *исходной* базе, отставание максимальных `id` от источника, опустевшие
по сравнению с прошлым разом таблицы, посторонние файлы, сбои уборки. Такие
случаи дают **код возврата 2** и текст в `status.json`, но копию не уничтожают.

Жёсткий отказ на мягких признаках был бы лечением хуже болезни: одна осиротевшая
строка в проде (её легко оставляет `alembic` или `manage.py` — `PRAGMA
foreign_keys` настраивается для каждого соединения) каждую ночь удаляла бы
исправную копию, и система осталась бы вовсе без бэкапов.

Коды возврата: `0` — чисто, `2` — копия есть, но есть предупреждения,
`1` — копии нет.

Сторож (`check`) читает **все** копии в каталоге, а не только свежайшую: копии
лежат на ext4 без контрольных сумм данных и без скраббинга, и если проверять
только последнюю, фактическая глубина восстановления равна одним суткам —
порча старых вскроется в момент, когда запасного варианта уже нет.

## Проверить руками

```bash
ssh homeserver 'systemctl list-timers report-backup*'
```

```bash
ssh homeserver 'python3 ~/report/backend/scripts/backup_db.py --dest ~/backups/report check'
```

```bash
ssh homeserver 'cat ~/backups/report/status.json; ls -lh ~/backups/report/'
```

Если что-то ругалось ночью:

```bash
ssh homeserver 'systemctl status report-backup.service report-backup-check.service --no-pager -l'
```

## Восстановление

Порядок важен: пока контейнер держит базу открытой, подменять файл нельзя —
приложение продолжит писать в старые `-wal`/`-shm` и затрёт восстановленное.

**1. Остановить сервис.**

```bash
ssh homeserver 'cd ~/report && docker compose stop report-backend && docker compose ps'
```

**2. Восстановить.** Скрипт сам проверит копию, отодвинет прежнюю базу вместе со
всеми её журналами и подменит файл одним атомарным движением.

```bash
ssh homeserver 'python3 ~/report/backend/scripts/backup_db.py --db ~/report/data/data.db --dest ~/backups/report restore --yes'
```

Восстановить не последнюю копию, а конкретную:
`restore --backup ~/backups/report/data-20260802-033000Z.db --yes`.

**3. Поднять сервис и убедиться, что он поднялся на этой базе.**

```bash
ssh homeserver 'cd ~/report && docker compose start report-backend && sleep 8 && docker compose logs --tail=25 report-backend'
```

В логе должны быть `alembic upgrade head` без ошибок и `Application startup
complete`. Порт 8000 наружу не опубликован (compose не публикует портов вообще —
наружу ходит только Caddy), поэтому `curl localhost:8000` на хосте не ответит.
Снаружи:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://report-analytics.ru/api/health
```

`/api/health` отвечает статикой и базы не касается, так что **окончательное
доказательство — войти в интерфейс и открыть список проектов**.

### Если restore отказывается: «data.db-shm на месте»

Это защита от подмены файла под работающим приложением. Но `-wal`/`-shm`
удаляются только при чистом закрытии последнего соединения, поэтому после
пропадания питания или `SIGKILL` они остаются лежать без единого живого
процесса. Убедитесь, что контейнера действительно нет:

```bash
ssh homeserver 'cd ~/report && docker compose ps'
```

Если `report-backend` не в состоянии `Up` — повторите команду восстановления
с `--force`.

### Откат самого восстановления

Прежняя база не удаляется, а отодвигается в `data.db.replaced-<время>` рядом с
рабочей, вместе со своими `-wal`/`-shm`/`-journal` и с правами `0600`. Убедившись,
что всё на месте, удалите их вручную — это полные слепки со всеми токенами, и
лежат они в каталоге, смонтированном в контейнер.

Если рабочей базы не было вовсе (восстановление на чистую машину), скрипт так и
скажет: «прежней базы на месте не было — откатывать нечего».

## Установка (один раз)

```bash
ssh homeserver 'mkdir -p ~/backups/report && chmod 700 ~/backups/report'
```

```bash
ssh homeserver 'sudo cp ~/report/deploy/homeserver/report-backup*.service ~/report/deploy/homeserver/report-backup*.timer /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now report-backup.timer report-backup-check.timer'
```

Каталог нужно создать **до** включения таймеров: unit'ы запускаются с
`ProtectSystem=strict` и списком `ReadWritePaths`, а несуществующий путь в этом
списке роняет запуск с невнятной ошибкой монтирования.

Пути и имя пользователя (`admin101`) в unit-файлах заданы явно — при переезде на
другую машину поправить их там.

## Чего эти копии НЕ закрывают

**Никто не узнает о провале сам.** Неудача видна только как упавший unit
(`systemctl --failed`) и запись в `status.json`. Канала оповещения нет: MTA на
сервере не настроен, поэтому штатная почта systemd никуда не уходит. Пока это
так, раз в пару недель стоит своими глазами смотреть `check` — или завести
уведомление (телеграм-бот в `OnFailure=`, healthchecks.io, что угодно).

**`~/report/.env` не копируется.** Восстановленная база без него бесполезна:
`SECRET_KEY` держит сессии, а сохранённые в базе OAuth-токены привязаны к
`YANDEX_CLIENT_ID`/`GOOGLE_CLIENT_ID` из этого файла. Полный комплект для
восстановления с нуля — репозиторий (в git) + `data.db` (здесь) + `.env`.
Пока `.env` придётся сохранить руками, например в менеджер паролей:

```bash
ssh homeserver 'cat ~/report/.env'
```

**Копии лежат на том же диске, что и база.** У сервера один SSD; отдельного
физического носителя нет. Это защищает от неудачной миграции, ошибки в коде,
случайного удаления данных и порчи файла — но **не от смерти диска**.

Закрыть остаток можно тремя способами, все требуют решения владельца:

1. внешний USB-диск в сервер — второй таймер с `--dest /mnt/backup/report`;
2. копирование на ноутбук по Tailscale (нужен запущенный SSH-сервер на ноутбуке
   и то, что он включён в момент копирования);
3. любое облачное хранилище через `rclone` — **обязательно с шифрованием**
   (`rclone crypt`): в файле лежат живые OAuth refresh-токены.

До этого момента считать, что от отказа диска сервис не защищён.
